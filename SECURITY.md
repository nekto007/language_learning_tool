# Обновление безопасности — 15 ноября 2026

Проверка кода, зависимостей и обычных HTTP-ответов сайта выявила реальные проблемы. Исправления требуют выкладки. Это не аудит операционной системы VPS и не гарантия отсутствия других уязвимостей.

## Что исправлено

- Имена и email в списке пользователей модулей больше не вставляются через HTML. Устранена возможность выполнения скрипта при просмотре администратором данных зарегистрировавшегося пользователя. Сообщения в соседних уведомлениях также выводятся как текст.
- Смена и сброс пароля отзывают старые браузерные сессии, remember-cookie, JWT access и refresh. У текущего браузера после обычной смены остаётся только свежая сессия. После сброса через письмо требуется новый вход.
- Ссылки сброса пароля строятся от настроенного `SITE_URL` с безопасным значением по умолчанию, а не от присланных заголовков Host/X-Forwarded-Host.
- Ограничения запросов используют адрес, полученный от доверенного прокси, а не произвольный первый адрес из X-Forwarded-For.
- Импортированный текст книг и предпросмотр редактора очищаются от активного HTML, сохраняя базовое форматирование.
- Загружаемые изображения ограничены по числу пикселей до декодирования. Убрано раздувание изображения в Python-список пикселей; уменьшение выполняется до копирования.
- HSTS включается на производственных HTTPS-ответах и без устаревшего Flask-параметра ENV.
- Обновлены библиотеки обработки изображений, HTML/XML, HTTP и другие зависимости с опубликованными предупреждениями безопасности.

## Выкладка

После получения кода на сервере:

```sh
docker compose build --pull web scheduler
docker compose up -d web scheduler
```

Для этого обновления новой миграции базы нет. Импортировать уроки и переносить MP3 не нужно. Пользователям, включая администратора, потребуется войти заново: старый формат сессий и старые JWT намеренно не принимаются. Пароли и учебный прогресс не изменяются.

Если перед приложением один nginx, он должен перезаписывать доверенные заголовки, а Gunicorn не должен быть открыт напрямую в интернет. Пример в `nginx/conf.d/app.conf` обновлён:

```nginx
proxy_set_header Host $host;
proxy_set_header X-Forwarded-Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $remote_addr;
proxy_set_header X-Forwarded-Proto $scheme;
```

В приложении доверяется ровно один прокси для адреса и протокола, X-Forwarded-Host не доверяется. При CDN или нескольких прокси нужно согласовать всю цепочку, а не увеличивать число доверенных узлов наугад. Файл nginx из репозитория не обновляет автоматически конфигурацию установленного на VPS nginx. После ручной правки сначала проверить `nginx -t`, затем перезагрузить конфигурацию обычным способом сервера.

`SITE_URL` должен указывать на настоящий HTTPS-адрес сайта, например `https://llt-english.com`. Значение из клиентского запроса для писем восстановления не используется. В образце nginx также отключён листинг каталогов.

## Проверка после обновления

1. Войти обычным способом, открыть первый урок и админку своей учётной записью.
2. В двух приватных окнах войти в один тестовый аккаунт. Изменить пароль в первом: первое остаётся доступным, второе после нового запроса должно потребовать вход. То же проверить через восстановление пароля.
3. Проверить HTTPS-заголовки, например `curl -I https://llt-english.com/login`: должны присутствовать HSTS, CSP, nosniff. Если HSTS отсутствует, проверить передачу HTTPS от фактического nginx/CDN или добавить HSTS в HTTPS-виртуальном хосте nginx.
4. Проверить загрузку обычного небольшого скриншота и чтение книги. Базовое выделение текста сохраняется; скрипты, обработчики событий и активные вставки из книги не поддерживаются.

## Что ещё требует отдельной работы

- Настройки и обновления VPS, SSH, firewall, фактические открытые порты и права файлов не проверялись через SSH. В compose PostgreSQL и web привязаны к localhost, но это не подтверждает все настройки живого сервера.
- Нужны резервные копии вне VPS и проверенная процедура восстановления. Наличие таких копий этой проверкой не подтверждено.
- Для администратора желательно внедрить второй фактор. Сейчас безопасность входа по-прежнему зависит от пароля и сохранности устройства.
- При нескольких Gunicorn-воркерах стандартный `memory://` хранит лимиты отдельно в каждом процессе. Для общих лимитов нужно внешнее общее хранилище либо ограничение на доверенном nginx. Защита от больших DDoS требует уровня хостинга/сети.
- CSP пока допускает существующие inline-обработчики интерфейса. Их последовательный перенос в JS позволит ужесточить политику. Не удалять разрешения целиком без проверки уроков.
- Контейнер запускается от root по текущему Dockerfile. Перевод на отдельного пользователя требует проверки прав на подключённые каталоги и отдельной выкладки.

## Зависимости и оставшиеся предупреждения

Сканирование выполнялось через pip-audit по версиям, разрешённым из текущих requirements в локальном Python 3.13, с учётом транзитивных зависимостей. Это не инвентаризация пакетов уже запущенного старого контейнера; новые версии вступают в силу после пересборки.

После обновления у 108 проверенных пакетов сырые предупреждения остаются только для setuptools 81.0.0. Уникальных записей две (база также возвращает дублирующую запись):

| Идентификатор | Условие | Решение |
| --- | --- | --- |
| CVE-2026-59890 / GHSA-h35f-9h28-mq5c | Построение sdist на файловой системе с Unicode-нормализацией, прежде всего macOS APFS/HFS+ | Linux-контейнер приложения не выполняет этот сценарий. Для распространения исходных пакетов с Mac использовать отдельное обновлённое build-окружение. |
| GHSA-xmj3-9gf7-h52w | Legacy-установка специально подготовленного wheel на Windows | Не является путём выполнения веб-запроса Linux-сервера. На Windows не использовать это окружение для установки недоверенных wheel. |

Setuptools сохранён на совместимой версии, поскольку текущий pymorphy2 импортирует удаляемый `pkg_resources`. Старая уязвимость обхода пути, исправленная в 78.1.1, обновлением закрыта. Для полного снятия оставшихся предупреждений нужен отдельный переход языкового модуля на поддерживаемую замену и затем обновление setuptools. Сырой сканер по-прежнему завершает проверку с ненулевым статусом; это не скрыто и не считается «нулём уязвимостей».
