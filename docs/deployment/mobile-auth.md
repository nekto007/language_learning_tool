# Нативная регистрация и вход на iPhone

Реализация от 17 ноября 2026 года для **llt-english.com**. Проект learn.llt-english.com не используется.

## Что сделано

- Вход по имени пользователя **или почте** и паролю. Существующие аккаунты, их прогресс и механизм обновления JWT сохранены.
- Нативная регистрация: имя, почта, пароль, уровень английского, согласие с политикой конфиденциальности. Аккаунт создаётся после ввода шестизначного кода из письма.
- Нативное восстановление пароля: письмо с кодом, новый пароль, затем обычный вход. Предыдущие JWT и браузерные сессии перестают действовать после смены пароля.
- Apple: системная кнопка и окно Sign in with Apple, проверка подписи, audience, issuer, срока и nonce на сервере, обмен authorization code. Проверка отзыва доступа при возвращении приложения на экран.
- Google: защищённое системное окно ASWebAuthenticationSession, серверный OAuth callback, затем одноразовое подтверждение с PKCE в приложении. Пароль Google приложение не получает. Это системный OAuth, а не встроенная страница сайта LLT.
- Новому пользователю соцвхода предлагается заполнить короткий нативный профиль. При совпадении почты с существующим LLT аккаунтом требуется его пароль; автоматического объединения по почте нет.
- Коды действуют 10 минут, после пяти неверных попыток нужен новый. Повторная отправка — через 60 секунд. Ограничения отправки дополнительно хранятся в БД и работают между процессами сервера.
- Письма отправляются после фиксации транзакции через отдельный обработчик. Планировщик повторяет попытки каждые 30 секунд, максимум три доставки на письмо. SMTP не задерживает ответ регистрации.
- Долгоживущие LLT токены остаются в Keychain. Приложение не содержит client secret Google или закрытый ключ Apple. В OAuth callback передаётся только короткоживущее одноразовое подтверждение, а не JWT пользователя.

Регистрация, смена пароля и первый соцвход требуют сети. Существующие локальные книги, кеш и отложенная синхронизация учебного прогресса сохраняют прежнее поведение.

## Обновление сервера

```sh
git pull
docker compose up -d --build
```

При запуске web штатная команда выполняет `flask db upgrade`. Новая миграция — `20261117_mobile_auth`, после `20261117_reader_vocabulary`. Добавляются таблицы подтверждений, ограничений отправки, очереди писем и привязок соцаккаунтов. Существующие данные пользователей не переписываются. Scheduler желательно перезапустить после успешной миграции web.

Публичная проверка без токенов:

```sh
curl --fail https://llt-english.com/api/mobile/auth/config
```

Поля `apple` и `google` остаются `false`, пока сервер не настроен. Скрытая кнопка в этом случае — ожидаемое поведение. Для регистрации и восстановления обязательно должны работать SMTP-настройки из `.env`: `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `EMAIL_USE_TLS`, `DEFAULT_FROM_EMAIL`. Сначала проверить доставку на собственный адрес, включая папку спама. В локальных автоматических тестах реальные письма не отправлялись.

## Google

В Google Cloud Console создать отдельный OAuth client типа **Web application** для мобильного входа LLT. Старые `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` относятся к Search Console и не меняются.

В Authorized redirect URIs указать **точно**:

```
https://llt-english.com/api/mobile/auth/google/callback
```

На сервере в `.env`:

```dotenv
MOBILE_GOOGLE_CLIENT_ID=<новый web client id>
MOBILE_GOOGLE_CLIENT_SECRET=<секрет этого клиента>
MOBILE_GOOGLE_REDIRECT_URI=https://llt-english.com/api/mobile/auth/google/callback
```

Настроить OAuth consent screen: название LLT English, домен llt-english.com, политика https://llt-english.com/privacy, поддержка и минимальные scopes `openid email profile`. В режиме Testing добавить свои тестовые Google аккаунты; для остальных пользователей перевести конфигурацию в подходящий публичный режим Google. Консольные требования Google могут зависеть от состояния проекта.

После перезапуска web `config.google` должен стать `true`, и кнопка появится без client secret в iOS. Google iOS SDK не требуется: возврат в приложение использует уже зарегистрированную схему `com.llt.english.ios://auth/callback`.

## Apple

Требуется команда Apple Developer с возможностью Sign in with Apple. Обычная установка приложения через бесплатную подпись остаётся доступна: Apple capability по умолчанию **не включена** в проекте.

1. В Apple Developer включить Sign in with Apple у App ID `com.llt.english.ios`. Если bundle ID изменён, синхронно изменить audience сервера, URL-схему и код возврата; текущая сборка рассчитана на указанный идентификатор.
2. Создать ключ Sign in with Apple, связанный с этим App ID. P8 хранить на сервере и в защищённом хранилище владельца, не в git и не в чате.
3. На сервере указать:

```dotenv
MOBILE_APPLE_ENABLED=true
MOBILE_APPLE_CLIENT_ID=com.llt.english.ios
MOBILE_APPLE_TEAM_ID=<Team ID>
MOBILE_APPLE_KEY_ID=<Key ID>
MOBILE_APPLE_PRIVATE_KEY=<PEM P8 с буквальными разделителями \n>
```

4. В Xcode у target LLT добавить capability **Sign in with Apple** и использовать entitlement `com.apple.developer.applesignin = [Default]`. Готовый шаблон — `LLT/AppleSignIn.entitlements`. Настройку `CODE_SIGN_ENTITLEMENTS` применить к нужным Debug/Release конфигурациям. Не затирать другие entitlements, если они уже используются.
5. В тех же конфигурациях установить пользовательскую build setting `LLT_APPLE_SIGN_IN_ENABLED = YES`. По умолчанию она `NO`, чтобы не сломать установку при неподходящем provisioning profile.
6. Обновить provisioning profile, пересобрать и проверить на физическом iPhone. Кнопка видна при одновременном разрешении сервера и сборки.

Apple refresh token хранится зашифрованно на сервере. Ключ шифрования производный от `SECRET_KEY`; менять этот ключ без миграции шифрованных данных нельзя. Смена ключа также делает недействительными ожидающие письма и подтверждения.

## Проверка владельцем после активации

- Создать тестовый аккаунт через почту, ошибиться в коде, ввести правильный, проверить тот же аккаунт на сайте.
- Сменить пароль; убедиться, что старый пароль и старые сессии больше не подходят.
- Войти через Google новым аккаунтом, заполнить профиль, выйти и повторить вход: профиль должен остаться тем же.
- Для существующей почты подтвердить пароль LLT и проверить сохранение книг и прогресса.
- Повторить с Apple, в том числе Hide My Email и повторный вход. Скрытый relay-адрес Apple считается отдельным адресом: приложение не пытается угадать, какому прежнему аккаунту он принадлежит.
- Отменить системное окно: вернуться ко входу без зависшего индикатора.

Реальные Google/Apple аккаунты и настройки провайдеров автоматически не менялись. Локальные проверки используют подписанные тестовые JWT, имитацию ответа провайдера и отдельное тестовое хранилище сессий. Они не заменяют финальную проверку с настоящими credentials и provisioning profile.

## Границы этой поставки

Настройки Google/Apple Console, реальная доставка SMTP и публикация в App Store требуют действий владельца соответствующих аккаунтов. Существующие пользователи с уже настроенными паролями продолжают входить прежним способом.

Удаление аккаунта из приложения и серверный отзыв Apple refresh token при удалении не входят в этот набор изменений. Их нужно закончить перед отправкой приложения с регистрацией в App Store: [требование Apple к удалению аккаунтов](https://developer.apple.com/help/app-review/guideline-reference/5-1-1-account-deletion). Аккаунт, созданный только через соцвход, может установить обычный пароль через восстановление по подтверждённой почте; при отсутствии доступной почты используется исходный соцвход.

## Локальные проверки

- iOS Core: 161 тест в 19 наборах, включая хранение сессии, PKCE, допустимые callback URL и совместимость прежнего Keychain.
- Сервер: 19 тестов мобильной авторизации; ещё 27 тестов существующего нативного обучения, управления словами и чтения прошли вместе с первоначальными 17 тестами авторизации. Отдельно проверены очередь писем, ограничение повторов и контекст планировщика.
- UI: пять сценариев на iPhone 16e; те же сценарии на iPhone SE, включая восстановление пароля после закрытия клавиатуры. Проверены светлая и тёмная темы, увеличенный системный текст.
- Финальная Release-сборка для generic iPhone (`CODE_SIGNING_ALLOWED=NO`) завершилась успешно. Подпись и запуск Apple/Google с реальными credentials остаются проверкой владельца.
- Проверки сервера используют временную SQLite БД. Живая база, реальные почтовые ящики и аккаунты провайдеров не изменялись. Конкурентные блокировки PostgreSQL не проверялись нагрузочным тестом.
