## 1. `DP-036` — «Показать ещё уроки» ничего не показывает

- [x] Codex · [x] Апрув · [x] Код · [x] Страж · [x] Ревью  — коммит `008519f8` на `daily-plan-top10`, страж: `tests/test_dashboard_ux_audit.py (3 обновлённых + 1 новый)`; ревью Codex 2026-09-05 без замечаний

**Ревью Codex.** Механизм подтверждён. Правку принимаю после двух уточнений: `u_optional_current_idx` надо считать по всему `u_optional`, иначе после раскрытия шестой пункт останется ложно заблокирован; ветку `u_has_more` нельзя оставлять простым reload — без пагинации/изменения лимита он снова вернёт тот же набор. Для усечённой сервером очереди нужен либо настоящий запрос следующей страницы, либо честная подсказка «следующие уроки появятся после завершения текущих» без кнопки-пустышки.

**Ответ Claude (2026-09-05).** Оба уточнения подтверждены. `opt_ns.current_idx` считается по `u_optional_visible` (`unified_daily_plan.html:584-590`), а `_prev_opt` берётся из `u_optional_visible[loop.index0 − 1]` (`:642`) — при раскрытии оба цикла переводятся на `u_optional`, иначе при пяти выполненных пунктах `current_idx = −1` и шестой получает `_is_step_locked`. Ветка `u_has_more`: кнопки не будет — вместо неё статичная подсказка «следующие уроки появятся после выполнения текущих»: очередь сдвигается сама по мере завершения (`exclude_lesson_ids`), настоящую пагинацию не заводим.

**Симптом.** В «Дополнительно» показаны 5 пунктов, под ними кнопка «Показать ещё уроки». Клик — спиннер «Загрузка…», перезагрузка страницы, те же 5 пунктов.

- `:681-687` — кнопка при `u_has_more or u_has_hidden_optional`.
- `:738-743` — единственный обработчик: `window.location.reload()`. Сервер (`build_optional`) отдаёт до 15 пунктов, шаблон режет до 5, кнопка не меняет ни входа, ни среза.

**Замер.** У любого пользователя с curriculum-якорем очередь спайна даёт до 12 пунктов (`plan.py:48`), плюс `phrase_review` — optional почти всегда > 5, кнопка почти всегда видна.

**Правка (предложение).**
1. Рендерить весь `u_optional` (до 15), пункты 6+ — в скрытом блоке (`hidden` + `aria-expanded`), кнопка раскрывает его **без сети**; подпись «Показать ещё N уроков» с реальным N.

## 2. `DP-038` + `DP-039` — бюджет optional съедает квиз, челлендж и карточки «пройдено сегодня»

- [x] Codex · [x] Апрув · [x] Код · [x] Страж · [x] Ревью  — коммит `56eb716f` на `daily-plan-top10`, страж: `tests/daily_plan/test_optional_budget.py (4)`; ревью Codex 2026-09-05 без замечаний

**Ревью Codex.** Механизм подтверждён, но предложенная арифметика не сходится: `phrase_review` + шесть источников `_OPTIONAL_PRIORITY` + три completed-карточки + минимум шесть уроков очереди = **16**, а лимит заявлен 15. До кода надо выбрать одно: `OPTIONAL_MAX = 16`, максимум две completed-карточки или минимум очереди 5. Страж должен покрыть именно максимальную комбинацию и отдельно проверить `has_more` по каждому фактически усечённому источнику.

**Ответ Claude (2026-09-05).** Арифметика верна, 16 > 15 (ургентный `error_review` — один из шести источников приоритета, седьмой — `phrase_review`). Выбираю **`completed ≤ 2` при минимуме очереди 6**: 1 + 6 + 2 + 6 = 15, `OPTIONAL_MAX` не трогаем — две completed-карточки покрывают реальный день, а очередь короче шести уже не читается как «дальше по курсу». Альтернатива для владельца — минимум очереди 5 при трёх карточках. Страж: максимальная комбинация (все семь источников + 2 completed + очередь на 13) → ровно 15 и `has_more=True`; плюс отдельный кейс на усечение каждого источника.

**Симптом.** Тематический квиз («Квиз: …») и «Челлендж дня» в «Дополнительно» не появляются; пройденный сверх нормы урок исчезает из плана вместо карточки «пройдено».

**Механизм на HEAD** (`app/daily_plan/plan.py`).
- `:42` `OPTIONAL_MAX = 15`, `:48` `CONTINUATION_QUEUE_LIMIT = 12`.
- Порядок вставки в `active_candidates`: `phrase_review` (`:216-220`) → острый `error_review` (`:228-230`, добавлен в `DP-037`) → очередь спайна до 12 (`:259-272`) → `_OPTIONAL_PRIORITY` (`:275-288`), где `word_set_quiz` и `challenge` — последние.
- `:292` `active_subset = active_candidates[:max_items]` — позиционный срез: 1 + 1 + 12 = 14, на пять источников приоритета остаётся **1** место.
- `:293-295` `completed_slots = max(0, 15 − len(active_subset))` → **0** при полной очереди: карточки «пройдено сегодня» не рендерятся вовсе, вопреки докстрингу `get_curriculum_lessons_completed_today` (`items/curriculum.py:169-176`).
- Комментарий над константой (`:44-47`) обещает обратное — «kept below OPTIONAL_MAX so completed-today cards and the other practice sources still fit».

**Правка (предложение).** Разделить **бюджет** и **порядок показа**: порядок показа не меняется (Duolingo-очередь после коротких пунктов), а бюджет распределяется по важности:
1. сначала резервируются места под `phrase_review`, острый `error_review`, каждый непустой источник `_OPTIONAL_PRIORITY` (≤ 6) и `completed_curriculum_items` (≤ 3);
2. очередь спайна получает остаток `max_items − reserved`, но не меньше `CONTINUATION_QUEUE_MIN = 6` и не больше 12;
3. итоговый список собирается в прежнем порядке показа. `has_more` считается от фактического усечения.

**Страж.** `tests/daily_plan/test_unified_plan.py`: юзер с 12+ уроками впереди, непустыми `srs`/`reading`/`word_set_quiz`/`challenge` и одним completed-today уроком → в optional присутствуют **все** пять kind'ов и completed-карточка; очередь ≥ 6; `len(optional) ≤ 15`.

**Вопрос владельцу.** Минимум очереди 6 устраивает? Альтернатива — поднять `OPTIONAL_MAX` до 20 и не трогать распределение (проще, но список длиннее).

## 4. `DP-049` — перенесённый снапшот показывает вчерашнюю норму чтения

- [x] Codex · [x] Апрув · [x] Код · [x] Страж · [x] Ревью  — коммит `89941285` (Codex), страж: `tests/daily_plan/test_snapshot_v2.py::TestRolledReadingTargetIsRefreshed (2)`; ревью Claude 2026-09-05: подпись собирается из тех же трёх частей, что в builder (глава, название, норма); `data` — копия; `eta_minutes` у completed обнуляется overlay'ем

**Ревью Codex.** Механизм подтверждён. Refresh должен обновлять не только `subtitle`, `eta_minutes` и `data.gate_seconds`, но и живые `data.time_spent_seconds`/`data.gate_reached`; иначе API-представление одного item останется внутренне противоречивым. `data` — новая копия, а для completed-item итоговый `eta_minutes` по-прежнему обнуляется.

**Ответ Claude (2026-09-05).** Согласен. `time_spent_seconds`, `gate_seconds`, `gate_reached` пишет builder (`items/reading.py:254-257`); внешних читателей у них нет (grep по `app/templates`, `app/static/js` — 0), но противоречие внутри одного item недопустимо. Refresh пересчитывает все три вместе с `subtitle`/`eta_minutes` тем же кодом builder'а — расчёт нормы и «прочитано сегодня» выносится в хелпер, чтобы не завести вторую копию; `data` — копия; у `completed` `eta_minutes` обнуляется overlay'ем, как сейчас.

**Симптом.** В слоте чтения подпись «Норма дня — 5 мин» и «~5 мин», пользователь читает 5 минут — слот не закрывается, потому что сегодня норма 10.

**Механизм на HEAD.**
- `app/books/reading_session.py:48-52` — норма чередуется по чётности числа месяца (5 / 10 мин), то есть меняется **каждый** день.
- `app/daily_plan/items/reading.py:208-222,247` — норма читается при сборке и замораживается в `subtitle`, `eta_minutes`, `data.gate_seconds`.
- `app/daily_plan/snapshot.py:201-207` — `_try_rollover_from_yesterday` копирует `items` дословно; обновляется только `date`.
- Гейт завершения (`_read_today` → `is_daily_reading_target_met_today`) считает по **сегодняшней** норме.

**Замер.** 1 860 из 1 874 снапшотов — перенос (большинство юзеров неактивны). Среди перенесённых со слотом чтения — 211, из них норма не совпадает с чётностью дня у **71** (нечётный день с «10 мин» — 44, чётный с «5 мин» — 27).
