# Постоянное улучшение: сквозной аудит 4 зон + ремедиация

## Overview

Свежий многоагентный аудит четырёх зон продукта — **UI**, **контент**, **разделы (blueprints/флоу)**, **админка** — с адверсариальной верификацией каждой находки, консолидацией в единый реестр `docs/audit/2026-08-08-cross-zone-audit.md`, и последующей ремедиацией по severity (P0 → P1 → отобранные P2).

Формат реестра и процесс копируют уже работающую в проекте схему двух предыдущих аудитов (`2026-06-13-100-edge-cases.md`, `2026-06-19-daily-plan-lesson-frontend-audit.md`): таблица находок с ID, severity-сводка, секция «Статус ремедиации» с коммитами.

Принцип: **аудит не правит код**, ремедиация не переоткрывает аудит. Между ними — гейт консолидации, где находки дедуплицируются и перепроверяются скептиками; в реестр попадают только CONFIRMED.

## Development Approach

- **Testing approach**: Regular (код, затем тесты) — кроме исправлений P0, где сначала пишется падающий регресс-тест, затем фикс
- Аудитные задачи (1–6) кода **не меняют** — только пишут в `docs/audit/2026-08-08-cross-zone-audit.md`
- Многоагентный паттерн: на каждую линзу — свой финдер; каждая находка перепроверяется независимым скептиком, настроенным опровергать; в реестр идут только CONFIRMED, PLAUSIBLE — в приложение
- Ремедиация — инкрементальными коммитами по группам находок, сообщения без упоминаний AI
- **CRITICAL: каждая ремедиационная задача ОБЯЗАНА включать новые/обновлённые тесты**
- **CRITICAL: перед переходом к следующей задаче — прогон `pytest`, ноль новых падений против baseline**
- Границы объёма: чинятся все P0 и P1 + те P2, что самодостаточны и низкорисковы. P3 и рискованные P2 остаются в реестре как открытые, с явным списком в финальной сводке
- YAGNI: не вводить новые абстракции, слои совместимости и «на будущее» — только то, что закрывает конкретную находку
